# adf-hx workarounds register

**What this file is for:** every place this codebase does something it would not otherwise do,
because `@alfresco/adf-hx-content-services` or `@alfresco/adf-core` requires it. It exists so the
cost of adopting adf-hx is countable rather than folklore.

**This file is gated.** Every marker in the codebase must have a row here, and every row naming a
code site must have its marker there — `scripts/review-guardrails.mjs`, `checkAdfHxWorkaroundIds()`,
run by the `guardrails` gate. A register with no gate decays the moment someone adds a
thirteenth workaround, so it has one. It was watched fail on purpose before being trusted.

| Marker in code             | Category                                    |
| -------------------------- | ------------------------------------------- |
| `WORKAROUND(adf-hx): W<n>` | 1 — workaround for an upstream defect       |
| `MISSING(adf-hx): M<n>`    | 2 — feature adf-hx does not provide         |
| `REFUSES: R<n>`            | 3 — a port that refuses                     |
| `DEGRADED(adf-hx): D<n>`   | 4 — known-degraded, deliberately not hidden |

Rows whose site is a `.json` file carry **no marker**, because JSON cannot hold a comment. Those
are listed with `— (config)` and the gate does not look for a marker in them.

**Audiences differ per category, which is why they are separated:**

- **Category 1** is for leadership and for whoever plans an adf-hx upgrade. Read the
  **Removable?** column before quoting a count. "Twelve workarounds" is not twelve things that
  eventually go away.
- **Category 2** is for product: these are features a customer sees, which upstream does not own.
  If we stop maintaining them, they disappear.
- **Category 3** is for whoever adopts the next component: it is the list of calls that throw.
- **Category 4** is for anyone who might otherwise report these as bugs. They are known.

Anything in here that is **upstream's fault** also appears in `docs/adf-hx-upstream-findings.md`,
which is written to be sent to the adf-hx team. This file is internal and includes things that are
nobody's fault.

Last updated: 2026-08-22. Versions: `@alfresco/adf-hx-content-services@7.20.0-automate.292`,
`@alfresco/adf-core@9.0.0`, `@angular/core@20.3.x`.

## Category 1 — Workarounds for upstream defects

**Read the last column before counting.** Six of the twelve are **structural**: they do not go away
when upstream fixes a bug, because they exist to reconcile two content models or two build
systems. Presenting twelve as twelve pieces of future cleanup would be wrong.

| ID  | What we do                                                                                                               | Why it exists                                                                                                                                                                                                                                               | Removable?                                                                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| W1  | `ng-mocks` replaced by a `file:` stub — `package.json` + `tools/stubs/ng-mocks/` — (config)                              | adf-hx's shipped `/ui` runtime bundle imports `ng-mocks`, a **test-mocking library** with two `eval()` calls, into a 1.6 MB customer chunk. The stub satisfies the import and throws if anything actually calls it.                                         | **Removable** when upstream stops importing it. Documented as **permanent** in the stub's README because that is the safe assumption, not because it is desired.                                         |
| W2  | `AppTranslateLoader` implements five undocumented methods — `apps/nuxeo-ui/src/app/i18n/app-translate-loader.ts`         | adf-core's `TranslationService` does not treat the ngx-translate loader as a `TranslateLoader`. It calls `setDefaultLang`, `providerRegistered`, `registerProvider`, `getFullTranslationJSON` and `init` on it. Absent → `TypeError` on boot.               | **Removable** only if upstream adopts the `TranslateLoader` interface. Until then structural: the alternative puts adf-core in the initial bundle.                                                       |
| W3  | Nine exact version pins — `package.json` — (config)                                                                      | adf-core declares **all sixteen** peers as unbounded `>=`, so a plain install floats `@angular/material-date-fns-adapter` to the Angular 22 line and the build dies with `Unsupported enum value`.                                                          | **Removable** when peers are bounded. Two pins differ from adf-core's own suggestion and would need re-deciding: `@mat-datetimepicker/core@16.0.1`, `pdfjs-dist@6.2.108`.                                |
| W4  | Initial bundle budget raised 2.0 → 3.5 → 4.0 MB — `angular.json` — (config)                                              | Eleven upstream `providedIn: 'root'` services force the port set into the **root** injector, which makes adf-core eager. Measured 1.70 → 3.49 MB.                                                                                                           | **Structural.** Not a defect to be fixed but a consequence of upstream's injector design. Only an architectural change upstream, or dropping adf-hx, moves it.                                           |
| W5  | Four manual asset globs — `angular.json` — (config)                                                                      | adf-core's i18n, adf-hx's i18n (×2) and adf-hx's icon set are all fetched at runtime from `assets/` and none is copied by installing the package.                                                                                                           | **Removable** if upstream ships an asset schematic or an `ng-add`. Purely mechanical today.                                                                                                              |
| W6  | adf-hx i18n catalogues **seeded** rather than left to register — `app-translate-loader.ts`                               | adf-hx components _do_ register their catalogues, via `provideTranslations` in each component's own `providers` — but registration happens at **component construction**, long after the language loaded. The registration lands; the strings never arrive. | **Removable** if upstream registers at bootstrap. Until then this is the only ordering that works.                                                                                                       |
| W7  | Five pipes provided as services — `libs/shared/adf-hx-bridge/src/lib/providers/provide-adf-hx-nuxeo-bridge.ts`           | `PropertyUtilService` injects `DecimalNumberPipe`, `LocalizedDatePipe`, `FileSizePipe` and `UserResolverPipe` as constructor services; `UserResolverPipe` injects `AsyncPipe`. None carries `providedIn`.                                                   | **Removable** if upstream marks them `providedIn: 'root'`. Note upstream's own `provideAdfEnterpriseAdfHxContentServicesServices()` is **not** sufficient — it covers adf-hx's pipes and not adf-core's. |
| W8  | `NuxeoDocumentRouterService` substituted for `DocumentRouterService` — `provide-adf-hx-nuxeo-bridge.ts`                  | adf-hx's router service hardcodes `/{repository}/documents/{id}` and feeds it straight to `[routerLink]`. This application has no such route.                                                                                                               | **Structural.** Any host with its own routes must substitute this. It has no `providedIn`, which suggests upstream intends it as a substitution point.                                                   |
| W9  | `::ng-deep` height and width overrides — `libs/features/browse/src/lib/browse-adf-hx-poc/browse-adf-hx-poc.scss`         | The versions and properties panels are built as drawers and ship `ViewEncapsulation.None` styles — `height: 100vh` on the version list, a fixed 370 px skeleton loader. Inside a tab they push the page past the viewport.                                  | **Removable** if upstream makes the panels layout-neutral. The selectors are upstream's class names, so a restyle shows up as a layout regression in evidence.                                           |
| W10 | Vitest `date-fns/locale` alias + `server.deps.inline` — `libs/shared/adf-hx-bridge/vite.config.mts`                      | adf-core's fesm bundle does a **directory** import of `date-fns/locale`, which Node's ESM resolver rejects outright. Vitest externalises `node_modules`, so a plain alias never sees the specifier.                                                         | **Removable** when adf-core imports `date-fns/locale/index.js`. Without it the bridge can only be tested against its own code, never against upstream services.                                          |
| W11 | A synthesised `sys` pseudo-schema in the model — `libs/shared/adf-hx-bridge/src/lib/mapping/nuxeo-to-hx-model.mapper.ts` | Upstream's `TOP_DEFAULT_PROPERTIES` are all `sys_*` and Nuxeo has no `sys` schema, so every one fell back to `FieldType.String`: `Created` rendered a raw ISO string, `Creator` rendered `[object Object]`.                                                 | **Structural.** `sys_*` is HxPR's system namespace; Nuxeo will never have it. Whoever bridges the two must declare it.                                                                                   |
| W12 | Nuxeo facet → HxPR mixin translation — `nuxeo-to-hx-model.mapper.ts`                                                     | `getFolderishTypes()` and `getFilishTypes()` filter on `SysFolderish`/`SysFilish`; Nuxeo says `Folderish` and, for a file, nothing at all. Without it the properties panel's Category selector renders empty.                                               | **Structural.** Two content models with different mixin vocabularies. Not a defect.                                                                                                                      |

**Count for leadership: 12 workarounds, of which 6 are structural** — W4, W8, W11, W12 outright,
and W2 and W10 structural in practice because the alternatives are worse. Six are genuinely
removable when upstream changes: W1, W3, W5, W6, W7, W9.

## Category 2 — Features adf-hx does not provide, rehomed to the host

These are not defects. Upstream's components are narrower than the hand-written ones they replaced,
and the difference had to go somewhere. **Product should know these are ours**: if we stop
maintaining them, the customer loses them, and no adf-hx upgrade brings them back.

Ours is driven by the Layer 1 descriptors, so `Reset` returns to the manifest rather than a packaged constant.                                                                                                                                                                                                                  |

## Category 3 — Ports that refuse

Every one throws with a message naming the operation. **None returns a plausible empty value** —
`AGENTS/11-beta-program.md` §3 records a port silently discarding its sort as the defect pattern to
avoid, and an empty array from a model or upload call is the same mistake with a bigger radius.

They are **bound rather than left unbound** deliberately: eleven upstream services inject their
tokens at construction, so an unbound token stops those services — and every component touching
them — constructing at all.

| ID  | Port and methods                                                                                              | Site                                                            | Why it refuses                                                                                                                                                                                                                                                                                | Fixable?                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| R1  | `UPLOAD` — all six: `createUpload`, `upload`, `complete`, `getUploadInfo`, `renewCredentials`, `deleteUpload` | `libs/shared/adf-hx-bridge/src/lib/api/nuxeo-unmapped-api.ts`   | HxPR uploads are a six-call chunked protocol with its own credential renewal. Nuxeo uses batch uploads — a different **lifecycle**, not a renamed endpoint.                                                                                                                                   | **Yes, with real work.** Belongs with whichever component first needs it.        |
| R2  | `MODEL` write half — `setModel`, `patchModel`, `setModelItemsForProject`, `getModelItemsForProject`           | `libs/shared/adf-hx-bridge/src/lib/api/nuxeo-model-api.ts`      | **Unimplementable.** Nuxeo's content model is server-side configuration deployed with a package or a Studio project; there is **no REST write path to call**. Per-project models do not exist in Nuxeo at all.                                                                                | **No.** Not unimplemented — unimplementable. The read half is fully implemented. |
| R3  | `QUERY.getDocumentsByQuery` — every HXQL statement except one                                                 | `libs/shared/adf-hx-bridge/src/lib/api/nuxeo-query-api.ts`      | HXQL queries the HxPR content model; Nuxeo speaks NXQL over a different one. It recognises upstream's document-versions statement **whole** and refuses the rest **by name**, because an unrecognised query answering with an empty result set is indistinguishable from an empty repository. | **Yes, per statement.** Adopting adf-hx search will need more.                   |
| R4  | `RENDITIONS.getRenditions` — not a discovery call                                                             | `libs/shared/adf-hx-bridge/src/lib/api/nuxeo-renditions-api.ts` | Returns a fixed `thumbnail, pdf` pair. Nuxeo exposes no rendition-enumeration endpoint through this bridge, so a caller asking "what renditions exist" cannot be answered truthfully.                                                                                                         | **Partly.** A Nuxeo enumeration endpoint would close it; none is exposed today.  |

## How to add a row

1. Put the marker in the comment at the site: `WORKAROUND(adf-hx): W13 — one line on why`.
2. Add the row here with the same ID.
3. Run `npm run beta:gate -- --gates guardrails`. It fails if the two disagree in either
   direction.
4. If the cause is upstream's, add it to `docs/adf-hx-upstream-findings.md` as well.

Do not delete a row when a workaround is removed. Strike it through and say which upstream version
fixed it — the history of what adf-hx cost is the point of the file.
